# 0004. 서비스명과 MVP 시연 범위 확정

- 상태: Accepted
- 날짜: 2026-06-13
- 관련 문서: `README.md`, `DEVELOPMENT.md`, `SPEC.md`, `ARCHITECTURE.md`, `TODO.md`, `ROADMAP.md`

## 맥락

초기 프로젝트는 `k-producthunt`를 가제로 사용했지만, 팀 논의 결과 서비스명을 `kick`으로 확정했다.

사내 행사 평가는 참신성, 완성도, 실용성을 본다. 팀은 MCP와 Skill을 통한 제작자 지원, Product 소개 페이지와 board 기반 탐색 경험, 실제 서비스 기반 seed 데이터, vote, newsletter UI를 중심으로 MVP를 시연하기로 했다.

운영자 큐레이션과 AI Slop 필터링은 실제 서비스에서는 필요하지만, 1주 MVP에서는 UI와 제작자 데모 완성도를 해칠 수 있다.

## 결정

서비스명은 `kick`으로 확정한다. 저장소명 `k-producthunt`는 초기 코드명으로만 유지한다.

MVP 시연은 아래 2개 플로우를 모두 보여준다.

- 탐색자 플로우: Weekly board, 검색/필터, Product 소개 페이지, vote, newsletter UI
- 제작자 플로우: Skill/MCP 제품 분석, 타겟 분석, 셀링 포인트, 피드백, 런칭페이지/카드뉴스/홍보 카피 초안, kick 등록 payload 준비 또는 제출

운영자 큐레이션 플로우는 MVP 시연에서 제외한다. 실제 서비스 기반 seed 데이터와 수동 콘텐츠 보정으로 완성도를 확보한다.

Newsletter는 MVP에서 실제 발송 없이 UI만 포함한다.

`kick contest`는 기존 contest 기능의 제품 표현으로 사용하되 MVP 핵심 시연 범위에는 포함하지 않는다.

## 고려한 선택지

- 탐색자 플로우만 시연: 구현 범위는 작지만 MCP/Skill의 참신성이 드러나지 않는다.
- 제작자 플로우만 시연: 참신성은 강하지만 서비스 탐색 플랫폼으로서의 완성도가 약해진다.
- 탐색자와 제작자 플로우를 모두 시연: 범위는 넓지만 평가 기준인 참신성, 완성도, 실용성을 모두 보여줄 수 있다.
- 운영자 큐레이션까지 시연: 실제 서비스 구조에는 가깝지만 1주 MVP에서는 범위가 과도하다.

## 결과

- 문서에서 서비스명과 기능명이 혼동되는 표현을 제거한다.
- `kick`은 서비스명으로 사용하고, 제작자 지원 기능은 제작자 런칭 보조 또는 제품 등록 보조로 부른다.
- 운영자 큐레이션 백엔드, AI Slop 필터링, 관리자 승인/검수는 후속 과제로 남긴다.
- 실제 서비스 기반 seed 데이터 준비가 MVP 완성도의 핵심 작업이 된다.
